# meta-deeptalk

코드를 건드리지 않고 한 주제를 깊이 이야기한다.
프로젝트 위치는 git 루트다. git 밖이면 지금 작업 폴더다.

## 넘지 않는 선

- 이 대화 동안 코드와 설정 파일을 고치지 않는다
- 새 파일을 만들지 않는다. 예외는 끝날 때 사용자가 승인한 대화 요약 문서 하나다
- 읽기 전용으로 찾아보는 것은 된다. 파일 읽기, 찾기
- 코드를 고쳐 달라는 말이 나오면 이 대화를 끝낸다. 다음 작업으로 스스로 넘어가지 않는다

## 다른 스킬과 다른 점

| | meta-deeptalk | brainstorming |
|---|---|---|
| 목적 | 탐색, 이해, 의견 교환 | 기능을 설계해 구현으로 넘긴다 |
| 코드 수정 | 하지 않는다 | 설계 뒤에 한다 |
| 결과물 | 고를 때만 요약 문서 | 설계 문서와 계획 |
| 끝나는 때 | 사용자가 끝내자고 할 때 | 계획 쓰기로 넘어갈 때 |

## 순서

늘 하는 것
1. 주제 잡기: 사용자가 무엇을 알고 싶은지, 무엇을 논의하고 싶은지 이해한다
2. 맥락 찾기: 필요하면 관련 코드와 문서를 읽기만 한다
3. 깊이 들어가기: 한 번에 질문 하나씩, 한 단계씩 들어간다

결정이나 합의가 목표일 때만 하는 것
4. 방향 내놓기: 두세 가지 방향과 장단점, 추천을 보여준다
5. 합의하기: 사용자와 방향을 맞춘다
6. 요약 남기기: 결론, 결정, 다음 할 일이 나온 경우만 한다

그냥 의견을 나누는 대화는 1~3에서 끝낸다. 매번 4~6까지 가면 설계 회의가 돼 버린다.

## 질문 방식

| 상황 | 방식 | 예 |
|---|---|---|
| 생각을 끌어낼 때 | 열린 질문 | 왜 그렇게 생각하세요? 다른 쪽에서 보면요? |
| 골라야 할 때 | AskUserQuestion 객관식 | A와 B 중 어느 쪽? |
| 장단점을 비교할 때 | 표와 짧은 설명 | 나란히 비교한 표 |

열린 질문과 객관식은 부딪히지 않는다. 쓰는 단계가 다르다. 넓힐 때는 열린 질문, 좁힐 때는 객관식이다.

## 대화 원칙

- 한 번에 질문 하나만 한다
- 짐작하지 않는다. 모르면 묻는다
- 넓게 퍼지지 않고 한 주제를 끝까지 판다
- 표와 그림으로 보여준다
- 동의하지 않으면 정중하게 반대하고 근거를 댄다

## 끝내기

끝내는 신호
- 말로 끝낼 때: 이 정도면 됐어, 고마워, 끝, 다른 거 하자
- 자연스럽게 끝날 때: 결론이 나고 더 묻는 것이 없다, 사용자가 다른 일로 넘어가려 한다

끝낼 때 꼭 하는 것
1. 요약을 남길지 판단한다
2. 끝났다고 분명히 알린다. 다음 작업으로 스스로 넘어가지 않는다

## 요약을 남기는 기준

남긴다. 하나라도 맞으면
- 결론이나 결정이 나왔다. 예: A 방식으로 하기로 했다
- 다음에 할 일이 생겼다. 예: 다음 주에 X를 검토한다
- 다시 볼 만한 장단점 비교가 쌓였다

남기지 않는다
- 그냥 의견을 나눴다
- 결론 없이 끝났다
- 사용자가 남기지 말라고 했다

남기기 전에 꼭 묻는다.
결론과 다음 할 일이 정리됐어요. docs/discussions/날짜-주제.md로 저장할까요?

승인하면 아래 형식으로 저장한다. 위치는 프로젝트 위치의 docs/discussions다.

```
# 주제

- 날짜: YYYY-MM-DD
- 참여: 사용자, Claude

## 배경
왜 이 대화를 했는지

## 핵심 논의
주요 질문과 답 요약

## 결론
합의한 방향이나 결정

## 다음 할 일
구현이나 검토가 필요하면 무엇을 해야 하는지
```

## 빠져나갈 신호

아래 말이 나오면 바로 끝낸다.
- 이거 구현해줘, 코드 짜줘
- 리팩토링해줘, 고쳐줘
- 이 버그 고쳐줘
- 테스트 더해줘
- 그 밖에 코드를 고쳐 달라는 말

끝낼 때
1. 끝났다고 알린다. 예: deeptalk를 끝냅니다. 코드 작업은 다음 메시지로 말씀해 주세요
2. 다음 스킬을 스스로 부르지 않는다. 다음 작업은 사용자의 다음 말에서 시작한다
3. 이어서 쓸 만한 스킬이 있으면 한 줄로 알려 줄 수는 있다. 강요하지 않는다. 없으면 말하지 않는다
